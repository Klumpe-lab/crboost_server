Investigated (2026-06-24) whether the RELION import job is necessary, to decide how to handle it under the afterok orchestrator (the P1.A IMPORT-command blocker). Grounded against a real succeeded project: `/groups/klumpe/crboost_data/post_handedness_fix/` (the on-disk successor to the renamed `GT` 412 project; same 20-TS / 9-job shape).

**The real import command is NOT `relion_import`.** The relion5 schemer runs the native python tool, BARE (not container-wrapped), from PROJECT ROOT:
`relion_python_tomo_import SerialEM --tilt-image-movie-pattern "./frames/*.eer" --mdoc-file-pattern "./mdoc/*.mdoc" --nominal-tilt-axis-angle <axis> --nominal-pixel-size <apix> --voltage <kV> --spherical-aberration <Cs> --amplitude-contrast <Q0> --optics-group-name <name> --dose-per-tilt-image <dose> [--invert-defocus-handedness] --output-directory Import/jobNNN/ --pipeline_control Import/jobNNN/`
(installed at `~/.local/lib/python3.10/.../tomography_python_programs/`, NOT in `relion5.0_tomo.sif`). So the current `_build_import_command` (`pipeline_orchestrator_service.py:526`, a `relion_import --do_movies --i ...` string) is wrong at every level. See [[project_orchestrator_replacement]].

**What import actually writes (tiny, fully registry-derived):**
- master `Import/jobNNN/tilt_series.star` `data_global`: 8 cols, 1 row/TS — rlnTomoName, rlnTomoTiltSeriesStarFile (project-rel pointer), Voltage, SphericalAberration, AmplitudeContrast, MicrographOriginalPixelSize, rlnTomoHand(±1), OpticsGroupName. Pure pointer+optics table; NO per-tilt data.
- per-TS `tilt_series/<TS>.star`: 6 cols, 1 row/tilt in ACQUISITION order — rlnMicrographMovieName (frames/...), TomoTiltMovieFrameCount, NominalStageTiltAngle (mdoc TiltAngle), NominalTiltAxisAngle (the user PARAM e.g. 84.4, NOT mdoc's 84.36), MicrographPreExposure (ACCUMULATED dose), NominalDefocus (mdoc TargetDefocus).
- Two subtleties to reproduce: dose must accumulate in acquisition order (registry `tilt_index`/`pre_exposure_e_per_a2` matches verbatim); tilt-axis is a persisted import param, NOT back-derived from mdoc.

**Particle processing does NOT depend on the import star.** Only `fsMotionAndCtf` (the first Warp step) consumes TILT_SERIES_STAR. The averaging jobs (subtomo_extraction→reconstruct_particle→class3d) each take one `optimisation_set.star` → particles.star + tomograms.star, all authored by OUR Warp/AreTomo ingest adapters (TsAlignment/TsCtf/TsReconstruct emit_star) from the TiltSeriesRegistry. No io_slots edge reaches the import star. **rlnTomoHand from import dies at fsMotionAndCtf — it's OVERWRITTEN by `WarpTools ts_defocus_hand` at tsCtf** (AreAnglesInverted in Warp XML → metadata_service.py), so import's handedness is moot for particles (relevant to the 412 saga). The per-TS `<TS>.star` is a LIVING doc each Warp job rewrites, growing 6→28 cols — that's the inter-job "recalculation" cruft worth demoting to a registry export.

**RELION is already "just a tool":** 4 of ~12 jobs invoke a relion binary (import; relion_tomo_subtomo; relion_tomo_reconstruct_particle; relion_refine); orchestration/DAG/metadata are ours. We ALREADY drive relion particle jobs from OUR-authored optimisation_set.star+tomograms.star with no relion import/align/ctf in that lineage (= "bring your own tomograms.star" already works).

**Decision options (user weighing, not yet decided):** A) keep+fix the relion command (smallest, keeps a binary on the path + the compute-node PATH problem); B) self-author tilt_series.star from the registry (kills the binary; low content risk since registry-backed; real cost = RELION GUI-openability fidelity = node-type labels + per-job job_pipeline.star, which P1.C builds anyway); C) drop import + rewire fsMotionAndCtf to the registry (purest, biggest blast radius: io_slots+DAG+input contract). Openability under B is preserved (node still on disk, authored by P1.C `export_relion_compat`); under C the open question is whether the GUI hard-fails on a missing Import node.

**Deepwiki answers (2026-06-24, 3dem/relion):** Q① **GUI does NOT hard-fail without an Import node** — `gui_mainwindow.cpp:1483-1505` dispatches tomo nodes by TYPE LABEL (LABEL_IMPORT_TOMOGRAMS / MOCORR / CTFFIND / TILTALIGN / EXCLUDE), not by import-job origin; nodes created "through different means" are fine. → **this de-risks Option C (drop import) too**, not just B; the only requirement is correct node-type labels (and the star must be valid for `relion_python_tomo_view` to VIEW it). Q④ structurally mandatory `tilt_series.star` global cols = only `rlnTomoName` (index) + `rlnTomoTiltSeriesStarFile` (per-TS pointer; relion's model drops it on internal read but it MUST be on disk — our fsMotionAndCtf reads it); plus the optics params the serialem importer sets. **USER DIRECTIVE: don't reason about "minimal mandatory" — mirror older successful projects' metadata verbatim (the oracle's exact 8 master + 6 per-TS columns), no trimming, no leaps.** Q② bring-your-own + Q③ optimisation-set already answered YES from our codebase.

**DECISION: Option B, inline-at-deploy — IMPLEMENTED 2026-06-24** (code-clean: py_compile + ruff; PENDING runtime — server has no auto-reload, needs `main.py` restart). In `pipeline_orchestrator_service.py`: new `_write_import_stars_inline(job_model, job_dir, project_dir)` writes the master `tilt_series.star` (8-col `global`) + per-TS `tilt_series/<TS>.star` (6-col, acquisition order) from `get_registry_for(project_dir).all_tilt_series()` + ImportMoviesParams (rlnTomoNominalDefocus sourced from the mdoc TargetDefocus by movie basename, defaults 0.0; rlnTomoTiltMovieFrameCount=1; rlnTomoHand=-1 if invert_defocus_hand else 1). `_submit_chain` prep-loop special-cases `JobType.IMPORT_MOVIES` → runs the writer inline, touches `RELION_JOB_EXIT_SUCCESS`, sets job SUCCEEDED + slurm_job_id=None, EXCLUDES from `prepared`; submit DAG now toposorts over `list(prepared)` so fsMotionAndCtf's afterok edge to import drops out (submits with no producer; star already on disk). `_build_import_command` reduced to a no-op (relion cmd dead on both paths). Schemer path (flag off) byte-identical. **Runtime gate:** deploy a scratch project with `use_afterok_orchestrator=true` and diff `Import/jobNNN/{tilt_series.star,tilt_series/*.star}` column-for-column vs the `post_handedness_fix` oracle (float decimal padding may differ — columns/values/order/hand-sign are what matter).
