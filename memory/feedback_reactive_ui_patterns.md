For all new UI work in this project, follow the patterns documented in `CLAUDE.md` under "UI reactivity patterns" and implemented in `ui/components/reactive.py`:

- **`FingerprintedView`** — any polling-driven view that would otherwise `container.clear()` + rebuild on every tick. Subclass it, implement `signature()` (cheap fingerprint of state inputs) and `render()`. The refresh becomes a no-op when nothing has changed.
- **`SingleFlight`** — any async handler that opens a dialog or does long work; guards against re-entry. `async with self.flight("key") as acquired: if not acquired: return ...`
- **Animations via CSS** — no server-driven `ui.timer` advancing a glyph. `@keyframes` in `ui/main_ui.py` (e.g. `.cb-braille-spin`).

**Why**: 2026-05-18 audit found that the pipeline roster's 3s status poll did `panel.roster_panel.clear()` + full rebuild on every tick — silently dropping clicks (button torn down before click handler fired) and resetting hover state. Symptoms the user described: "rows don't react to cursor for a few seconds," "first few clicks on add are dropped," "species dialog disappears and gets replaced by another identical one." Root causes: full-tree refresh on every poll + no re-entry guard on dialog openers + 0.17s `ui.timer` + `ui.run_javascript` broadcast for spinner frames.

**How to apply**: When writing any new panel/widget/tray that has a polling timer or refresh callback, reach for `FingerprintedView`. When writing any handler that opens a dialog, wrap in `SingleFlight`. When you want an animated visual indicator, write CSS `@keyframes` — never a server-side advance loop. If a refresh is unavoidably tree-replacing (no signature can capture all inputs), at minimum guard against rebuilding when triggered from an idle tick rather than a user action.

**Already converted (2026-05-18)**: `RosterWidget` in `ui/pipeline_builder/pipeline_roster.py`, `_BackgroundTaskTray` in `ui/background_task_tray.py`, `prompt_species_and_add` in `ui/pipeline_builder/pipeline_builder_panel.py`. **Intentionally NOT touched**: the tomo dashboard dialog (user said "it's quite workable"); its `refresh_all` is still clear+rebuild.

**Gotcha (2026-05-21): `ui.run_javascript` from a handler that deletes its own element crashes** with "The parent element this slot belongs to has been deleted." `ui.run_javascript` resolves the client via `context.slot.parent`; if the handler already did `.clear()` on (or rebuilt) the ancestor that owns the handler's element, that slot's parent is gone. Two fixes used in `tomo_dashboard_dialog.py`: (1) capture `client = ui.context.client` at render time and call `client.run_javascript(...)` (try/except) instead of the slot-based `ui.run_javascript`; (2) order operations so the element owning the running handler isn't deleted until after any `run_javascript` has run (e.g. render_main before render_sidebar in `select_ts`). Bind handlers to a STABLE ancestor (a container that survives `.clear()`) rather than a child that gets recreated, when feasible.

**Gotcha (2026-06-09): a long-lived `ui.dialog` opened from an async click handler is DESTROYED by the dashboard's `refresh_all`** — "the window just closes as if the page rerendered behind me." Root cause is framework-level (verified in NiceGUI 3.0.3 `events.handle_event`): an async handler runs inside `with arguments.sender.parent_slot:`, so any element created in the handler — including a dialog — parents under the SENDER's slot. The "Curate in ArtiaX" button lives in the dashboard's `main_area`, and the 4 s live-refresh does `main_area.clear()` → the dialog's ancestor is gone → it closes. (Aggravated 2026-06-09 by folding curation-dir `.coords` mtimes into the refresh signature, which made the bundle-write itself trigger a rebuild ~4 s after opening.) **Fix = parent the dialog at the PAGE layout slot, which is never cleared: `with context.client.layout.default_slot: with ui.dialog() ...`.** Done for `open_curation_control_center` (`ui/curation_session_dialog.py`), which also became a single STABLE-layout panel (status chip + Start/Stop swap-in-place + targeted `set_text`/`set_visibility` updates, NO `body.clear()` shape-shifting) per the user. **The SAME latent bug exists in the other dashboard dialogs** (`_open_merge_dialog`, `_open_manual_coords_path_dialog`, the dedup panel) — they just don't bite because they're short-lived (closed before a 4 s tick); parent them the same way if any becomes long-lived.

**Gotcha (2026-06-11): don't put per-tick task PROGRESS in a signature that gates a full DOM rebuild.** The journey dashboard's 4 s `_maybe_refresh` is signature-gated (good), but its signature included each running task's `(id, progress_current, progress_total)` — so every progress tick of a long generation job (preview/cutout render over a big recon on Lustre, seconds per item) moved the signature → `refresh_all()` → `main_area.clear()` + full rebuild. User: "the whole page is jittery, rebuilds every ~10 s." Fix: the signature observes task **membership** (`tuple(sorted(t.id for t in active))`) + finished-set + curation-save mtimes — NOT progress. A task START (id appears) and FINISH (id leaves → enters finished-set) each still trigger exactly one rebuild (placeholder → result); intermediate progress does not (it lives in the tray, which has its own poll). Rule: a rebuild-gating signature should fingerprint only what the rebuilt DOM actually *displays* — progress bars belong to the tray, so progress must not be in the main-pane signature. Also added a `logger.info("journey live-refresh rebuild (changed: tasks|tasks-done|curation-save)")` at the rebuild point so any lingering loop is diagnosable from the log (the dashboard has no auto-reload — see [[reference_hpc_env]]).
