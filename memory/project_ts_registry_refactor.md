Direction approved 2026-04-12 after the tsCTF metadata merge failure (`Path(key).stem` corrupting filenames with tilt-angle dots + `[:num_entries]` slice dropping late-dose tilts from `warp_df`).

**Why:** Identity is currently a recomputed accident at each metadata-merge site (three different `cryoBoostKey` derivations in `metadata_service.py`). This breaks at scale and silently corrupts at boundaries. User wants TS/Frame/Tomogram as first-class primitives with IDs assigned at import and carried unchanged through the pipeline. Goal is bulletproof + scale to 100s of TS per project.

**How to apply:**
- Staged rollout, each stage ships independently:
  - Stage 0: bug fixes in `_parse_tilt_series_xml` (Z-indexing) and `_merge_ctf_metadata` (drop broken `base_key`) — DONE
  - Stage 1: `services/tilt_series/` package (models.py, registry.py, build.py); sidecar persistence at `{project}/registry/{index.json, tilt_series/{ts_id}.json}`; wired into `ProjectService.initialize_new_project` (new projects) and `load_project_state` (legacy backfill); exposed as `backend.registry_for(path)` — DONE
  - Stage 2: `services/tilt_series/adapters/ts_ctf.py` — `TsCtfIngestAdapter` replaces `MetadataTranslator.update_ts_ctf_metadata` in `drivers/ts_ctf.py:263`. Verified against pos9_10 project: CTF values match legacy byte-for-byte — DONE
  - Stage 3: `FsMotionCtfIngestAdapter`, `TsAlignmentIngestAdapter`, `TsReconstructIngestAdapter` under `services/tilt_series/adapters/`; swapped at `drivers/fs_motion_and_ctf.py`, `drivers/ts_alignment.py`, `drivers/ts_reconstruct.py`. All three smoke tested against pos9_10 byte-for-byte vs on-disk legacy STARs (motion+CTF: 10×8 cols, alignment: 10×5, reconstruct: 2×6). `_assert_ts_identity_consistency` moved into `TsAlignmentIngestAdapter.ingest` as a precondition — DONE (2026-04-12)
  - Stage 3 hotfixes (2026-04-12): registry build was using the SOURCE mdocs glob (bare names like `Position_11.mdoc`) while downstream STARs use project-prefixed names (`test_20251113_412_Position_11`). Fixed `_build_and_persist_registry` to read from `{project}/mdoc/*.mdoc` (post-import prefixed copies); `load_project_state` now detects drift (registry TS IDs disjoint from project mdoc stems) and rebuilds. Added `preflight_registry` in `drivers/array_job_base.py`, called by all 4 supervisors before `submit_array_job` — fails in <1s with a diagnostic dump if the registry doesn't cover the expected TS, replacing the "waste an hour then fail aggregation" mode. Also bumped `FsMotionCtfParams.perdevice` default 1→2 and `fsMotionAndCtf.mem` 16G→24G in both `config/conf.yaml` and `config/conf.template.yaml` — observed ~3-4 min/TS motion correction, perdevice=2 ~halves it.
  - `ts_import` filter resolution (2026-04-13): real-project runs on test3_ then test4_20251113_412 hit `TsAlignmentIngestAdapter.emit_star` failures ("frame X has no alignment in registry output (tomostar did not include this movie)"). Confirmed via sha256 trace that WarpTools `ts_import` itself drops 6-7 frames/TS (not our code). Source: `WarpTools/Commands/Tiltseries/ImportTiltseries.cs:335-350` contains a hardcoded contiguous-run outward-from-0-tilt intensity filter (`AverageIntensity >= MinIntensity * cos(angle) * MaxAverage * 0.999f`) that truncates everything past the first failing tilt per side. Cannot be disabled — CLI validation rejects `--min_intensity < 0`, and zero-mean motion-corrected MRCs produce negative-median `AverageIntensity` that still fails `>= 0` with `MinIntensity=0`. No verbose/debug flag. Downstream WarpTools treats the post-filter tomostar as authoritative (`TiltSeries.InitializeFromTomoStar` in `WarpLib/TiltSeries/TiltSeries.cs:311-359`) — `ts_aretomo`/`ts_ctf`/`ts_reconstruct` never re-read `warp_frameseries/*.xml`. **Resolution**: matched legacy CryoBoost silent-skip idiom from `src/warp/tsAlignment.py:132-140` — in `_apply_alignment_to_tilt_df` (ts_alignment adapter) and `_apply_ctf_to_tilt_df` (ts_ctf adapter), `continue` on a frame with no registry entry instead of raising. Initialize the 5 alignment columns to NaN so the schema stays consistent. Output STARs retain all 41 rows; filtered rows are cosmetic. `ts_reconstruct` iterates per-TS, unaffected. Rejected Stage 4.5 (`Frame.is_filtered_at_import`) as overkill — legacy idiom is ~10 lines, matches the battle-tested prior implementation, and downstream behavior is identical. `TsImportParams.min_intensity` default was bumped 0.3 → 0.0 (still doesn't fully disable the filter, but raising it is now non-fatal; DANGER comment on the field is accurate). Full writeup in TS_REGISTRY_REFACTOR_PLAN.md "`ts_import` filter: resolved…" section.
  - Stage 4: registry-driven STAR emission pre-submit (STARs become regenerable serialization, not source of truth)
  - Stage 5: `registry.can_run()` gates in UI + `assert_complete` preflight in drivers
  - Stage 6: lazy per-TS load for 100+ TS projects
  - Stage 7: retire `WarpXmlParser`, `MetadataTranslator`, `cryoBoostKey`
- Key identity decisions: Frame.id = raw frame filename stem (debuggability > prettiness); Tomogram 1:1 with TS for v1; overwrite-on-rerun.
- RELION compatibility preserved: STARs still written on disk in the same format, just driven by registry state.
- Per-job adapter pattern: each job defines `emit_star(registry, job_dir)` and `ingest_results(registry, job_dir)`; no string archaeology in the hot path.
