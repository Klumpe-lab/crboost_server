The user has a firm, RECURRING UI aesthetic and has corrected "material-UI-style" chrome more than once (verbatim 2026-06-25: "I have no idea why you keep doing these material ui-style tabs in HUGE CAPS LOCK font and buttons are bad too"). When building ANY UI:

- **Replicate the dashboard / Journey toolbar styling** — the compact `cb-*` classes in `ui/dashboard/css.py` (`.cb-section-card-header`, `.cb-section-admin`, `.cb-chip` / `.cb-chip-strip`): tight gaps, small fonts (~10–11px), geometric layout, color + font weight altered ONLY when it carries meaning. Subtle borders/backgrounds, not bold material surfaces.
- **Avoid raw Quasar/material defaults.** NO `ui.tabs()`/`ui.tab()` material tabs — they render big UPPERCASE labels; use compact custom tabs/segments. NO chunky `ui.button(...).props("color=primary")` — use small, flat, geometrically-aligned controls.
- **THE text button is `house_button()`** (`ui/components/buttons.py`, landed 2026-08-21): 22px slate-outline-on-white, 10px Plex Sans, **core look INLINE on the element** + `color=None` (NiceGUI defaults to color='primary' = blue Material pill); hover states in `ui/dashboard/css.py`. Variants `accent` (dark-slate fill, ONE per dialog/page) and `danger` only. Section actions right-pinned (`ml-auto` — workbench `_action_button`). Native number spin arrows killed in `ui/dashboard/css.py`. Mode switches with height-varying panels: grid-stack + visibility-hidden via INLINE styles (`_stacked_panels`, template_workbench.py).
- **CSS delivery trap (burned 2026-08-21):** `ui.add_head_html` at module level (main_ui.py) = baked into the page shell, which this deployment serves STALE — new rules there never reached the browser (buttons stayed blue, panel stack rendered all-visible with a dead switch). The reliable channel is `ui/dashboard/css.py` `ensure_assets_loaded()` (injected per client AFTER connect, over the socket). Structural styling → inline on the element; pseudo-elements/hover/polish → dashboard/css.py; NEVER new rules in the main_ui shell block. The `.cb-field`/`.cb-select` rules are mirrored in both for this reason.
- **"Species" page is user-facing named "Particles registry"** (renamed 2026-08-21; internal code names stay `species`/`workbench`).
- **Separation = whitespace, NOT gray rules** (user 2026-08-21: "prefer slightly bigger vertical space between sections rather than a gray line"): page sections use `PAGE_SECTION_STYLE` (12px, _field_styles.py) + `gap-5`; no `section_rule()` under page-level titles; obvious hint tails ("click a row to select") deleted, informative ones fold into the title tooltip. Inputs must flow with surrounding text: `.cb-field` = 16px control / 10px font — a box 2× its neighbor's font height is "way too huge". Side-by-side list columns (workbench templates|masks) get FIXED-height scrolling lists (186px) so the blocks below align across columns and growth never reflows the page.
- **Color budget is tight (user 2026-10-15: "The amount of color in the app in places where it doesn't need to be is really annoying to me these days").** Utility icons are grey: slate `#475569` active, `#cbd5e1` disabled — no indigo/purple accents. Species identity on dense rows is a grey glyph (`particle.svg`) named on hover, not a colored pill. Color stays for state only (status lights, counts). No purple anywhere for state (queued = light-blue `#60a5fa` ring). Status lights = flat dot + soft same-color halo only — a specular glint / rim shading was rejected as "analogue … 90s RPG" (user 2026-10-15): minimal, never skeuomorphic.
- **Reuse the project's file explorer** rather than re-rolling path inputs; EXPAND the shared component when functionality is missing so other parts of the project benefit too (candidates: `ui/glob_directory_input.py` — dir text + autocomplete, no real browse; `ui/pipeline_builder/files_tab.py` — file listing). The user wants real browse + multi-select, not a bare glob field.

**Why:** density + consistency. The user runs a dense, technical workspace; oversized material chrome wastes space and clashes with the existing dashboard. **How to apply:** when a new dialog/panel is needed, copy the dashboard's compact chrome conventions FIRST; only introduce new color/font when it's meaningful (e.g. a red WIP marker — and keep those subtle too).
