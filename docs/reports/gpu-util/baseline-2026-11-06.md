# GPU, CPU and memory use of crboost jobs, read from SLURM accounting (2026-11-06)

What each crboost job on partition `g` used of what it asked for, from `sacct`, since the move to CBE.next
(2026-11-01). Produced by `scripts/sacct_gpu_report.py`, which is read-only and repeatable:

    python3 docs/reports/gpu-util/scripts/sacct_gpu_report.py --since 2026-11-01 --scope all --completed-only

How to read the columns:

- **busy %** is nvidia-smi's `utilization.gpu` as SLURM records it (`gres/gpuutil`): the share of sampled instants at
  which some kernel was running. It does not say how much of the GPU the kernel used. Sampled every 30 s, divided by
  the job's GPU count (SLURM sums it over GPUs), weighted by GPU-seconds.
- **slice** rows are MIG `1g.23gb` slices. SLURM records 0 for them whatever they did, so busy is left out ("n/a").
- **busy < 10 %** and **noGPUmem** count jobs that were almost never busy / never allocated a byte of GPU memory
  (`gres/gpumem` maximum 0). A job in both asked for a GPU and did not use it.
- **CPU eff** is CPU time over elapsed × allocated CPUs; **mem eff** is MaxRSS over the requested memory.
- **read / write GB** are SLURM's disk counters; what they count has not been checked (miss_align's 5 TB read is its
  pool of training cubes in `/tmp`, so they include more than the network).
- A job's driver is read from its stored batch script, keyed by the job's own directory (the `StdOut` path; a
  single job's `WorkDir` is the project, not the job). Driver `?` is a job whose script SLURM did not show: other
  users' jobs, and the `pytest -m cluster` probes.

Thin data: six days, three users, most of the jobs from the migration week's benchmarks and tests. Failed, cancelled
and running jobs are left out; each table says how many GPU-hours they held. The window moves as jobs finish, so a
rerun differs by the jobs that completed since.
